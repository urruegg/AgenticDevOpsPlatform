## 2. Primary Store — Azure Cosmos DB (NoSQL API)

### 2.1 Why Cosmos DB
- Single-digit-millisecond latency for agent context lookups.
- Elastic scale and multi-region writes for global agent deployments.
- Native vector / semantic search if/when retrieval-augmented patterns are
  added.
- Per-tenant isolation via partition keys.

### 2.2 Containers (planned)

| Container | Partition Key | Purpose |
|-----------|---------------|---------|
| `agent-runs` | `/agentRunId` (or HPK: `/tenantId/agentRunId`) | One document per agent turn: inputs, tools called, outputs, latency, cost |
| `agent-sessions` | `/sessionId` | Conversation-level metadata |
| `drift-reports` | `/subscriptionId` | Latest drift scan per subscription |
| `policy-cache` | `/policyId` | Cached enterprise policy snippets (TTL) |

### 2.3 Partition Key Rules
- **High cardinality** (`agentRunId`, `sessionId`, `subscriptionId`).
- **Hierarchical Partition Keys (HPK)** when a single logical partition could
  exceed 20 GB (e.g., long-lived tenants).
- Avoid low-cardinality keys (`status`, `region`).

### 2.4 SDK Patterns
- **Singleton `CosmosClient`** per process.
- Honour `429` retry-after; log SDK diagnostics on latency spikes or
  unexpected status codes.
- Use `async` APIs; never block the event loop.
- Set preferred regions for read locality.

## 4. Retention & PII
- **PII**: avoid storing raw user prompts containing PII. Redact at ingest.
- **Retention defaults**: 90 days for traces, longer (180–365) for audit
  records tied to deployments.
- **Right to erasure**: by-design via `tenantId` + `userId` indexed queries.

## 5. Backup & Recovery

- Bicep files versioned in ADO repo (Git is the source of truth).
